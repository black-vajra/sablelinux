## Architecture decision: Secure Boot support

Decision:
Make Secure Boot a priority supported SableLinux capability,
with the long-term objective of recommending it by default
on compatible production hardware.

This is a future engineering workstream, not an immediate
Beta 1 release blocker.

### Security profiles

1. Developer / Compatibility
   - Secure Boot disabled
   - Custom kernels and experimental modules supported
   - Full development flexibility retained

2. Secure Boot
   - Authenticated boot chain
   - Signed release boot artifacts
   - Controlled module-signing policy
   - Documented key enrollment and recovery

3. Advanced Hardware-Backed Security
   - Secure Boot plus optional TPM 2.0 measured boot
   - Optional PCR-bound LUKS2 unlocking
   - Recovery and boot-integrity verification

### Preferred initial architecture

Investigate signed Unified Kernel Images (UKIs)
containing the kernel, initramfs, command line,
and relevant metadata.

Prefer user-controlled Secure Boot keys for initial
implementation.

Evaluate Microsoft-signed shim support later for
broader firmware compatibility and easier enrollment.

Private signing keys must never enter Git, live media,
rootfs staging trees, or publicly distributed artifacts.

Signing, key rotation, revocation, rollback, and
recovery must be documented and tested.

### Validation requirements

Follow the established testing hierarchy.

Tier 1:
Validate kernel, initramfs, and userspace behavior.

Tier 2:
Validate Secure Boot under OVMF.

Required tests:

- Valid signed UKI boots successfully.
- Unsigned UKI is rejected.
- Modified or incorrectly signed UKI is rejected.
- Authorized kernel updates remain bootable.
- Revoked or superseded keys are handled correctly.
- Recovery and rollback paths work as documented.

Later tiers:
Validate installer integration and physical hardware.

### Release engineering requirements

Secure Boot artifacts must be generated through the
canonical Z890 release pipeline.

Record:

- Source Git commit
- Kernel version
- Build and signing tool versions
- Public signing certificate fingerprint
- Signing policy version
- Artifact SHA256 hashes
- Validation results

Keep private signing material separate from public
release metadata.

Secure Boot alone does not guarantee root filesystem
integrity or eliminate firmware-level threats.
