### NET-03 — SSH packaging findings

The distributed sshd.service contains:

    Wants=sshdgenkeys.service
    After=sshdgenkeys.service

The referenced service is absent from the installed system.

Manual execution of ssh-keygen -A generated the required host keys.
The daemon subsequently started and survived a reboot.

The missing weak dependency is a confirmed packaging defect.
A corrected first-start or first-boot key-generation mechanism remains
to be implemented and validated on the canonical build host.

The installed sshd_config also contains developer-specific port and
username restrictions.

A historical sshd_config backup is present in the installed filesystem.

Keyboard-interactive authentication was enabled in the effective
configuration despite disabled password authentication. No dynamic PAM
linkage was observed. This does not independently establish whether
keyboard-interactive authentication could successfully authenticate.

### NET-04 — Public release SSH policy

Operator decision:

- Ship upstream OpenSSH configuration defaults rather than the
  developer's private infrastructure configuration.
- Do not impose developer-specific usernames or SSH ports.
- Keep the SSH network service disabled until explicitly enabled.
- Preserve the separately established release security requirement
  prohibiting direct remote root login.
- Generate host keys independently on each installed machine.
- Do not distribute authorized client keys or private client identities.
- Exclude historical administrative configuration backups.
- Apply private fleet policy through separate post-install provisioning.

The canonical implementation must reconcile upstream defaults with the
explicit remote-root-login security requirement.

### NET-06 — Dual-stack full-tunnel failure

Initial WireGuard activation requested IPv4 and IPv6 default routes.

Successful stages:

- WireGuard interface creation.
- Application of cryptographic configuration.
- IPv4 interface address assignment.
- MTU configuration.
- Firewall mark assignment.
- IPv6 alternate default-route installation.

Failure occurred during IPv6 policy-rule creation:

    RTNETLINK answers: Address family not supported by protocol

Independent execution of ip -6 rule show produced the same error.

The physical interface possessed an IPv6 link-local address.
IPv6 addressing therefore exists, but IPv6 policy routing is unavailable.

The failed activation removed the WireGuard interface.

Investigate CONFIG_IPV6_MULTIPLE_TABLES on the canonical kernel.
The exact kernel configuration cause remains unverified.

### NET-07 — IPv4 full-tunnel failure

A temporary private deployment sysctl configuration disabled IPv6
globally and for newly created interfaces.

The WireGuard configuration was changed to IPv4-only full-tunnel
routing for further testing.

Successful stages:

- IPv4 alternate routing table creation.
- Firewall-mark-based routing rule creation.
- Main-table default-route suppression.
- Setting net.ipv4.conf.all.src_valid_mark.

Failure occurred during legacy iptables rule installation:

    Warning: Extension comment revision 0 not supported, missing kernel module?
    iptables-restore: line 3 failed

The failed operation removed the temporary interface and IPv4
policy-routing rules.

Complete rollback of all incidental kernel state, including
src_valid_mark, was not independently verified.

### NET-08 — Netfilter capability audit

Confirmed built-in components:

- x_tables
- ip_tables
- iptable_raw
- iptable_mangle
- iptable_filter
- nf_conntrack
- wireguard

Confirmed available loadable components:

- xt_addrtype: loaded.
- xt_mark: module available.

Unavailable in the installed kernel/module tree:

- xt_comment
- xt_connmark

Investigate:

- CONFIG_NETFILTER_XT_MATCH_COMMENT
- CONFIG_NETFILTER_XT_CONNMARK

Distinguish kernel configuration omissions from module installation,
dependency-index or release-staging omissions.

The installed kernel configuration was unavailable through
/proc/config.gz and the expected /boot/config-<release> location.

Review CONFIG_IKCONFIG, CONFIG_IKCONFIG_PROC and retained kernel
configuration artifacts.

### NET-09 — Temporary administrative VPN

Full-tunnel activation remains blocked by the observed kernel
networking deficiencies.

A temporary split-tunnel configuration was implemented, routing only
the private VPN subnet through WireGuard.

Full-tunnel DNS and policy-routing hooks were removed from the active
configuration. The earlier configuration was preserved locally.

Verified:

- Successful interface activation.
- Successful cryptographic handshake.
- Bidirectional communication with the VPN relay.
- Zero packet loss in the three-packet relay connectivity test.
- Correct routing to other VPN peers.

Ordinary internet traffic continues to use the physical network.

This configuration is for remote administration only. It is not a
full-tunnel privacy VPN and provides no internet kill switch.

### NET-10 — Restricted peer-to-peer forwarding

Initial communication between the administrative workstation and
Pavilion failed in both directions.

Investigation established:

- Both clients could communicate with the VPN relay.
- Client routing was correct.
- Pavilion SSH listener was operational.
- Pavilion legacy iptables filter policies were ACCEPT.
- Relay IPv4 forwarding was enabled.
- Relay routes to both peers were correct.
- Relay forwarding policy was default-drop.
- No explicit forwarding authorization existed for the tested pair.

Added narrowly scoped forwarding rules permitting:

- Administrator-initiated SSH to the Pavilion.
- Established SSH replies.
- Administrator-initiated ICMP echo requests.
- Corresponding ICMP echo replies.

Unrestricted peer-to-peer access was not enabled.

Verified firewall counters, successful peer ping and authenticated
SSH over the WireGuard interface.

Persisted the validated rules in the existing firewall configuration.
Configuration syntax validation passed.

The firewall was not reloaded because its configuration contains a
global flush ruleset directive, which can remove dynamically managed
Fail2ban tables.

The existing Fail2ban table remained present.

Relay reboot persistence has not been tested.

### NET-12 — IPv6 persistence discrepancy

After reboot:

- net.ipv6.conf.all.disable_ipv6 = 1
- net.ipv6.conf.default.disable_ipv6 = 1

However, the physical Ethernet interface again possessed an IPv6
link-local address.

Complete IPv6 disablement and leak prevention are not established.

Investigate interface-specific sysctl values and network-manager
initialization order.

Do not present the temporary sysctl workaround as a distribution
default or a verified privacy guarantee.

### NET-13 — Additional private infrastructure concern

The Pavilion SSH daemon listens on wildcard addresses.

The tested local IPv4 filter policies accept all traffic.

Remote access through the VPN relay is restricted, but the relay
firewall does not establish a restrictive local-host firewall policy.

Review device-local SSH exposure separately. Do not equate
VPN forwarding restrictions with endpoint firewall protection.

## Architecture Decisions

1. Distribution configuration and private fleet provisioning must
   remain separate.
2. Z890 remains the sole authoritative kernel and release build host.
3. Physical installations are validation targets.
4. Successful manual provisioning must become documented and
   reproducible.
5. WireGuard full-tunnel compatibility must be functionally tested.
6. Kernel configuration and module availability require separate
   verification.
7. No private infrastructure credentials or machine identities are
   authorized release contents.
8. Temporary deployment workarounds must not silently become
   distribution defaults.
